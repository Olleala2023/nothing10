## Карта документации

Каждая тема живёт ровно в одном файле. Если одно правило написано в двух местах — это баг
документации: они разойдутся. Дублировать нельзя, ссылаться нужно.

| Документ | О чём | Когда читать |
|---|---|---|
| `CONTRIBUTING.md` (этот файл) | Процесс работы, критерии готовности, как менять правила | Перед первой задачей |
| `docs/ARCHITECTURE.md` | Что где лежит, границы модулей, сборка и деплой | Перед изменением структуры |
| `docs/CODE_STYLE.md` | Стиль JS / CSS / HTML, обязательные паттерны и запреты | Перед написанием кода |
| `docs/TESTING.md` | Что и когда тестируем, правило «тест раньше кода» | Перед новой функцией |
| `docs/DECISIONS.md` | Журнал решений: почему сделано так, а не иначе | Когда правило кажется странным |
| `DEPLOYMENT_GUIDE.md` | Настройка Cloudflare Pages, домен, почта | При работе с инфраструктурой |
| `ANALYTICS_GUIDE.md` | Варианты аналитики и их влияние на приватность | При работе с метриками |
| `AUDIT_2026-07-25.md` | Аудит: 38 находок с приоритетами | Как источник задач |
| `README.md` | Описание продукта для внешнего читателя | Не является правилами |

**Открытые решения.** В `docs/DECISIONS.md` две записи со статусом 🔴 Открыто (позиция по
трекингу, лицензия). Пока они не закрыты, соответствующие файлы трогать нельзя — иначе
расхождение вырастет. Ограничения указаны прямо в записях.

## Уровни требований

В документации используются три уровня — как в RFC 2119. Это не украшение: без явного
уровня любое правило читается как пожелание.

- **НУЖНО** — обязательно. Нарушение блокирует merge. Исключение возможно только с записью
  в `docs/DECISIONS.md`.
- **СТОИТ** — сильная рекомендация. Отклонение допустимо, если в описании коммита есть
  причина.
- **МОЖНО** — разрешённый вариант, выбор за автором.

## Рабочий процесс

### Ветки

НУЖНО вести работу в отдельной ветке. Прямые коммиты в `main` запрещены: `main` —
это то, что прямо сейчас работает у пользователей, Cloudflare Pages деплоит его автоматически.

Формат имени: `<тип>/<краткое-описание-латиницей>`

```
fix/timer-resets-on-screen-off
feat/wake-lock
docs/development-rules
refactor/checklist-modules
chore/deps-update
```

### Коммиты

НУЖНО использовать Conventional Commits — по ним генерируются changelog и `lastmod` в sitemap.

```
<тип>(<область>): <что изменилось, в императиве>

<зачем — если из заголовка неочевидно>
```

Типы: `feat` · `fix` · `refactor` · `docs` · `test` · `chore` · `perf` · `style`

Области: `app` · `landing` · `tools` · `research` · `legal` · `sw` · `build` · `docs`

```
fix(app): keep countdown running when the screen turns off

The blur and visibilitychange handlers reset the timer, so a phone
locking its screen after 30s made the main use case impossible.
Countdown is now derived from an absolute timestamp.
```

Правила по содержанию:

- НУЖНО: один коммит — одно смысловое изменение. Правка бага и переформатирование файла —
  два коммита, иначе диff нечитаем.
- НУЖНО: заголовок до 72 символов, в императиве («add», не «added» и не «adds»).
- НЕ НУЖНО: коммиты с сообщением `fix`, `update`, `wip`. Через полгода они не значат ничего —
  в истории проекта таких уже больше десяти.
- НЕ НУЖНО: упоминать в сообщении модель ИИ, версию ассистента или номер сессии.

### Pull request

PR обязателен для изменений категории M и L (см. ниже). Для S — МОЖНО коммитить в ветку и
мерджить без ревью, если проверки прошли.

В описании PR НУЖНО указать: что изменилось, зачем, как проверялось, и ссылку на запись
в `docs/DECISIONS.md`, если решение архитектурное.

## Классификация изменений

Единая шкала для всего процесса: от неё зависят требования к тестам, ревью и записи решения.
Категория определяется **риском**, а не количеством строк.

| | **S — мелкое** | **M — среднее** | **L — крупное** |
|---|---|---|---|
| Что это | Текст, стили, контент, опечатки, правка одного значения | Новая функция внутри существующего модуля, рефакторинг без смены контракта | Новый модуль, смена архитектуры или стека, работа с таймером/статистикой/Service Worker/юридическими текстами |
| Тесты | Не нужны | Вместе с кодом | **До кода** |
| Ревью | Не нужно | Нужно | Нужно |
| Запись в DECISIONS | Не нужна | Если отменяет правило | Нужна |
| Пример | Поправить формулировку на странице | Добавить экспорт рефлексий | Перевести таймер на absolute timestamp |

**Правило разрешения спора:** если сомневаетесь между двумя категориями — берите старшую.
Ошибка в сторону лишнего теста стоит полчаса, ошибка в другую сторону уже стоила продукту
основного сценария использования (см. аудит, п. 1.1).

**Отдельно:** изменения в `src/app/app.js` (таймер, статистика, стрики), `public/app/sw.js`
(кеширование) и `public/legal/*` (юридические тексты) — **всегда минимум M**, независимо от
размера диффа. Это места, где однострочная правка уже ломала продукт.

## Критерии готовности

Чеклист перед тем, как считать задачу завершённой. Для категории S достаточно пунктов 1–4.

1. Код соответствует `docs/CODE_STYLE.md`; запрещённых конструкций нет.
2. `npm run build` проходит без ошибок и предупреждений.
3. Отладочные `console.log` удалены (см. `CODE_STYLE.md` → «Логирование»).
4. Изменение проверено вручную в браузере — в тёмной и светлой теме, на узком экране.
5. Тесты написаны по правилам `docs/TESTING.md` и проходят.
6. Если правился баг — есть тест, который падал до исправления.
7. Документация обновлена, если изменение затронуло структуру, сборку или поведение,
   описанное в `README.md` или гайдах.
8. Новых противоречий в документации не появилось (см. «Как менять правила»).

## Проверки

**Текущее состояние — честно:** автоматических проверок в проекте пока нет. ESLint стоит
в зависимостях, но без конфигурации и без скрипта запуска; тестов и CI нет вообще. Это
крупнейший пробел, зафиксированный в аудите (п. 3.11).

Целевой набор команд:

```bash
npm run build      # работает сейчас
npm run lint       # предстоит настроить: eslint.config.js + скрипт
npm test           # предстоит настроить: vitest
```

НУЖНО: пока `lint` и `test` не настроены, пункты 5 и 6 критериев готовности выполняются
вручную и осознанно, а не считаются неприменимыми. Отсутствие инструмента — не отсутствие
требования.

## Как менять сами правила

Документ правил гниёт по трём причинам, и все три уже случились в этом проекте. Ниже — что
с ними делать.

### 1. Правило вне git — это не правило

Правила хранятся в репозитории и меняются коммитом с ревью. Локальные файлы вне версионного
контроля не считаются правилами ни для человека, ни для AI-ассистента (см. `DECISIONS.md`,
запись 0005 — именно так предыдущий набор правил и потерялся).

### 2. Дублирование гарантирует противоречие

НУЖНО: одна тема — один документ. Если правило нужно в двух местах, во втором стоит ссылка,
а не копия.

Так возникли текущие противоречия: описание структуры проекта есть и в `README.md`, и в
`DEPLOYMENT_GUIDE.md` — и они разошлись между собой и с реальностью. Утверждения о трекинге
разъехались по шести файлам (`DECISIONS.md`, 0003).

### 3. Правило без причины невозможно оспорить

НУЖНО: у каждого неочевидного правила либо короткое «почему» на месте, либо ссылка на запись
в `DECISIONS.md`. Правило, чью причину никто не помнит, одинаково опасно и соблюдать,
и нарушать.

### Порядок изменения правил

1. Меняете правило — сначала запись в `docs/DECISIONS.md`, потом текст правила.
2. Проверяете, не сказано ли то же самое в другом документе. Если сказано — удаляете копию,
   ставите ссылку.
3. Обновляете дату «Последний пересмотр» в затронутом документе.
4. Коммит типа `docs` с объяснением, что изменилось в правилах и почему.

### Что описывать словами, а что нет

НУЖНО: если правило можно проверить машиной — проверяйте машиной, а в документе оставляйте
одну строку со ссылкой на конфиг. Отступы и переносы строк живут в `.editorconfig`, стиль
кода — в конфиге ESLint. Правило, существующее только в прозе, соблюдается ровно до первого
дедлайна.

Словами описывается то, что машина проверить не может: границы модулей, что считать источником
правды, когда нужен тест, почему выбран подход.

### Пересмотр по расписанию

НУЖНО: раз в полгода пройти по всем документам из карты и сверить с кодом. Дата следующего
пересмотра — в заголовке каждого документа. Пересмотр, привязанный только к «когда
понадобится», не происходит никогда — это и есть история этого проекта.

Быстрая проверка на актуальность: взять из документа три конкретных утверждения (путь к
файлу, имя команды, название директории) и проверить в репозитории. Если хоть одно неверно —
документ пора вычитывать целиком.

## Язык

Разделение сознательное — сейчас в проекте языки перемешаны внутри одного файла
(`DEPLOYMENT_GUIDE.md` содержит русские и английские инструкции вперемешку, в
`src/app/app.js:421` русский комментарий среди английских).

- **Русский:** документация в `docs/`, `CONTRIBUTING.md`, аудит, журнал решений — рабочий
  язык владельца проекта.
- **Английский:** код и всё, что живёт в коде или рядом с ним — идентификаторы, комментарии,
  JSDoc, сообщения коммитов, имена ветвей, текст интерфейса, `README.md` (внешний читатель).

НУЖНО: не смешивать языки внутри одного файла.
